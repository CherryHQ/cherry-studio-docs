# 跨模型交叉复核重要产出

对外发布前的重要文案、译文或技术方案，单个模型的输出很难自证可靠。这个案例用一个外部 MCP 服务器（bayze-mcp）把"多个模型互相检查"固化为可复用的工作流：一个模型起草，另一个厂商的模型做结构化评审，评审不通过时自动修订——每一步用到的模型、耗时和费用都记录在本地日志里。

适用场景：对外声明、合同相关译文、发布说明、需要把关的重要邮件。日常问答和简单翻译不需要这么重的流程。

## 推荐组合

* 【对话】+ MCP 服务器 bayze-mcp：把多模型协作注册为工具，对话中一句话触发；
* 不同厂商的模型凭证（例如 DeepSeek、通义、豆包各一个 Key）：交叉复核的价值来自厂商差异，同一家模型互查意义有限；
* 本地 YAML 配置文件：声明工作流和预算上限，密钥只放环境变量。

## 操作流程

{% stepper %}
{% step %}
### 1. 安装并配置 MCP 服务器

bayze-mcp 是一个开源（MIT）的本地路由器，在【设置】→【MCP】→【MCP 服务器】添加：命令 `npx`，参数 `-y bayze-mcp mcp --config /path/to/config.yaml`。配置文件声明"谁起草、谁评审、谁修订"以及费用上限；API Key 通过环境变量注入，不写进配置文件。

```
npx -y bayze-mcp mcp --config ~/bayze-config.yaml
```
{% endstep %}

{% step %}
### 2. 在对话中触发复核工作流

配置好后工具列表会出现 `list_workflows` 和 `run_workflow`。直接说："用 review_then_revise_cn 处理：[内容]"，助手会调用工作流：模型 A 起草 → 模型 B 以 JSON 格式给出"通过/需修改 + 具体理由" → 不通过时模型 C 按意见修订。
{% endstep %}

{% step %}
### 3. 看结构化结果决定是否采用

工作流返回每一步的模型、耗时、token 与费用估算，以及评审结论原文。评审意见是模型判断而非事实保证——发布决策仍由人做，但"哪个模型在什么环节说了什么"全程可追溯。
{% endstep %}
{% endstepper %}

{% hint style="info" %}
字数、格式这类硬约束建议写进任务描述并让引擎检查，而不是口头要求模型"控制在 N 字以内"——模型自报字数经常不准。bayze-mcp 内置确定性检查，超限直接拦截。
{% endstepper %}

<details>

<summary>为什么不用多模型对比功能就够了？</summary>

【对话】的多模型对比适合快速看分歧；当产出需要"必须经过评审才能定稿"的流程约束、以及预算控制和留痕时，用工作流引擎固化更合适。两者可以并用：对比找方向，工作流出终稿。

</details>
