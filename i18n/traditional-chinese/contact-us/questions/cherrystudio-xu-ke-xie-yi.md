## 先理解三項結論

1. **開放原始碼不代表禁止商業使用。** Cherry Studio 官方儲存庫明確允許在完整遵守 AGPL-3.0 的前提下，將社群版用於商業用途。
2. **商業使用不代表可以封閉原始碼。** 修改、散布或透過網路向他人提供功能時，可能觸發授權條款中的原始碼、授權聲明與網路互動義務。
3. **需要豁免 AGPL-3.0 要求時，應申請商業授權。** 商業授權屬於另一份協議，不會由本頁自動授予。

## AGPL-3.0 允許什麼

在遵守授權條款的前提下，AGPL-3.0 允許：

* 執行軟體。
* 閱讀與研究原始碼。
* 修改軟體。
* 複製與再次散布原始版本或修改版本。
* 對軟體收費或在商業環境中使用。

「自由軟體」描述的是使用、研究、修改與分享的自由，不代表所有服務、部署或支援都必須免費。

## 何時需要重點檢查義務

| 情境 | 需要重點閱讀的內容 |
| :--- | :--- |
| 只在自己的裝置上執行官方版本 | LICENSE 全文、第三方元件授權、免責聲明 |
| 修改後在組織內部使用 | 修改範圍、可存取者、是否發生散布或遠端網路互動 |
| 向客戶或其他主體散布安裝套件 | AGPL 第 4–6 節的聲明、授權文字與 Corresponding Source 要求 |
| 散布修改版本 | 修改聲明、以相同授權條款授權、Corresponding Source |
| 讓使用者透過網路與修改版本互動 | AGPL 第 13 節關於向遠端使用者提供 Corresponding Source 的要求 |
| 整合到封閉原始碼產品或服務 | 作品邊界、組合方式、相依關係及是否需要商業授權 |

{% hint style="info" %}
「內部使用」、「網路服務」、「外掛程式」、「獨立程序」或「只修改少量程式碼」等說法，本身不足以得出合規結論。應結合實際架構、交付對象與適用法律判斷。
{% endhint %}

## 散布軟體時的常見義務

散布 Cherry Studio 或其修改版本時，通常需要注意：

* 保留適用的著作權與授權聲明。
* 向接收者提供 AGPL-3.0 授權文字。
* 明確標示自行修改的版本與相關日期。
* 以 AGPL-3.0 授權受涵蓋的完整作品。
* 依授權條款允許的方式提供對應原始碼。
* 不施加與 AGPL-3.0 衝突的額外限制。
* 不以技術措施阻止接收者行使授權條款授予的權利。

具體要求與提供原始碼的方式，請以 LICENSE 第 4–7 節原文為準。

## 透過網路提供修改版本

AGPL-3.0 與 GPL v3 的重要差異之一，是遠端網路互動。

如果你修改了程式，並讓使用者透過電腦網路遠端與該修改版本互動，而該版本支援此類互動，AGPL 第 13 節要求向這些使用者明顯提供取得該版本 **Corresponding Source** 的機會。取得方式應透過網路伺服器免費提供，並使用標準或慣常的複製方式。

不應將此要求簡化為「所有伺服器程式碼都必須公開」，也不能簡化為「只要不散布安裝套件就沒有義務」。需要判斷哪些程式碼構成受授權條款涵蓋的作品及其對應原始碼。

## 什麼是 Corresponding Source

Corresponding Source 不是任意上傳一個原始碼壓縮檔。授權條款將其定義為修改該作品所需的首選原始碼形式，通常還可能包括：

* 建置、安裝與執行目的碼所需的原始碼。
* 控制這些操作的指令碼。
* 該作品專門依賴的介面定義與相關原始碼。
* 你對受涵蓋作品所做的修改。

系統程式庫、通用工具及可從其他原始碼自動重新產生的部分，可能依授權條款的定義排除。應根據實際建置與交付方式核對。

## 第三方元件與內容

Cherry Studio 儲存庫與安裝套件可能包含採用不同授權條款的相依套件、字型、圖示、模型資訊或其他資源。

AGPL-3.0 適用於 Cherry Studio 受其涵蓋的程式碼，不會自動以 AGPL-3.0 取代第三方元件的獨立授權條款。再次散布前應同時檢查：

* 儲存庫與安裝套件附帶的第三方聲明。
* 相依套件自身的授權條款與 NOTICE 要求。
* 商標、Logo、圖片、字型與資料集的個別授權。
* 你新增的程式碼與資源是否有權再次散布。

## 商標與品牌

軟體授權不等於 Cherry Studio 名稱、Logo 或其他品牌資產的商標授權。

如果計畫發布衍生產品、重新包裝安裝套件、對外宣傳合作關係或使用官方品牌素材，應先確認品牌使用範圍，不應讓使用者誤以為衍生版本由 Cherry Studio 官方發布或擔保。

## 無擔保與責任限制

AGPL-3.0 第 15–17 節包含無擔保與責任限制條款。在法律允許的範圍內，軟體依現狀提供，品質、效能與適用性風險由使用者承擔。

如果組織需要服務等級、賠償、專門支援或其他保證，應透過個別商業合約確認，不應從開放原始碼授權中推定。
