# Настройка сервисов моделей

Сервисы моделей — это точки доступа для вызова больших языковых моделей, моделей зрения, моделей эмбеддингов и моделей переранжирования в Cherry Studio. Здесь настраиваются учетные данные поставщиков услуг, адреса запросов, протокольные конечные точки и списки моделей; о регистрации и получении ключей для каждого поставщика см. [Сервисы моделей](../../../pre-basic/providers/).

{% hint style="info" %}
Различные платформы могут называть учетные данные API Key, секрет, токен или Token. Их конкретный формат и права определяются поставщиком услуг, и это не означает, что ключи с разных платформ взаимозаменяемы.
{% endhint %}

## Включение сервиса модели

Перейдите в:

> **Настройки → Сервисы моделей**

В левой части — список поставщиков услуг, а в правой — настройки подключения и модели для выбранного поставщика.

Список поставщиков услуг поддерживает:

- Поиск по названию поставщика, названию модели или ID модели;
- Просмотр включенных, отключенных, всех или подходящих для агентов поставщиков услуг;
- Изменение порядка отображения перетаскиванием;
- Разворачивание нескольких экземпляров, созданных в одном пресете;
- Копирование, редактирование или удаление управляемых поставщиков через контекстное меню;
- Нажатие на **+** рядом с полем поиска для добавления пользовательского поставщика.

Если все поставщики услуг отключены, список автоматически отобразит всех поставщиков услуг, что удобно для первоначальной настройки.

## Настройка встроенных провайдеров

### 1. Выбор и включение провайдера

Выберите провайдера слева и активируйте переключатель в правом верхнем углу.

Переключатель провайдера определяет только то, доступен ли этот провайдер в приложении, но не гарантирует, что API Key, адрес и модель настроены правильно.

### 2. Ввод API Key

Вставьте API Key, созданный в панели управления провайдером, в поле **API Key**.

Справа от поля ввода обычно доступны:

- Показать/скрыть Key;
- Скопировать Key;
- Открыть управление несколькими ключами;
- Проверить соединение.

Некоторые провайдеры используют OAuth, учетные записи облака или авторизацию устройства и могут не иметь стандартного поля ввода API Key. В этом случае следует войти или заполнить параметры учетной записи облака в соответствии с процедурой соответствующего провайдера.

{% hint style="danger" %}
Никогда не размещайте реальные API Key в скриншотах, публичных репозиториях, чатах или вложениях обратной связи. Перед созданием скриншота закройте отображение ключа; если вы подозреваете утечку, немедленно отзовите старый ключ в панели управления провайдером.
{% endhint %}

### 3. Проверка адреса запроса

Встроенные провайдеры обычно предоставляют адрес API по умолчанию. Если вы не используете прокси, совместимый шлюз или частное развертывание, рекомендуется оставить значение по умолчанию.

Примеры распространенных базовых URL:

```text
https://api.example.com/v1
```

Не добавляйте `/chat/completions`, `/responses` или `/messages` к базовому URL только потому, что в документации провайдера показан полный пример запроса. Cherry Studio сгенерирует путь запроса в зависимости от типа конечной точки модели.

Если адрес был изменен, интерфейс может предложить **Восстановить значение по умолчанию**. Вход для настройки запросов также позволяет управлять адресами конечных точек и пользовательскими заголовками для различных протоколов.

### 4. Проверка соединения

Нажмите **Проверить соединение** справа от поля ввода API Key.

В текущей версии V2 откроется панель проверки, где вам нужно будет выбрать:

- Активированный API Key;
- Добавленную и пригодную для проверки модель.

Проверка выполнит фактический запрос к выбранной модели. Успешное соединение гарантирует только то, что эта комбинация ключей, адреса, конечной точки и модели может выполнить базовый вызов, но не гарантирует доступность всех моделей, изображений, вызовов инструментов или запросов с большим контекстом.

## Управление несколькими API ключами

Нажав кнопку **Список ключей** рядом с полем ввода ключа, вы сможете:

- Добавлять несколько ключей;
- Прикреплять к ключам понятные метки;
- Включать или отключать отдельные ключи;
- Редактировать, копировать или удалять ключи;
- Просматривать количество активных ключей.

Во время работы ключи будут циклически использоваться по порядку среди включенных ключей. Отключенные ключи не участвуют в ротации; если нет ни одного включенного ключа, обычный поставщик API-ключей не сможет выполнить запрос.

{% hint style="warning" %}
В старых версиях часто использовалась запятая для ввода нескольких ключей в одно поле. V2 лучше подходит для управления каждым ключом по отдельности через список ключей, что позволяет присваивать им отдельные имена, отключать и проверять их, а также избежать случайного использования запятых или путаницы с метками.
{% endhint %}

Ротация нескольких ключей не обходит квоты на уровне учетной записи поставщика услуг, организационные ограничения или условия использования. Несколько ключей в одной учетной записи могут использовать общий счет и лимиты.

## Адреса API и конечные точки

### Базовый URL

В большинстве случаев вводите корневой адрес сервиса или корневой путь версии, например:

```text
https://api.example.com/v1
```

Относительно того, нужен ли `/v1`, следует руководствоваться документацией поставщика услуг и предустановленными настройками Cherry Studio. Адрес должен быть действительным URL с `http://` или `https://`.

### Полные конечные точки и `#`

Если совместимый интерфейс предоставляет только полный конечный путь, можно оставить `#` в конце адреса, чтобы Cherry Studio распознала его и не продолжала конкатенацию этого пути. Например:

```text
https://api.example.com/custom/chat/completions#
```

Такой синтаксис используется только в том случае, если поставщик услуг явно указывает нестандартный полный путь. К распространенным распознаваемым конечным точкам относятся:

- `chat/completions`
- `responses`
- `messages`
- `generateContent`
- `streamGenerateContent`
- Конечные точки для генерации или редактирования изображений

В обычный Base URL `#` добавлять не следует.

### Многопротокольные конечные точки

Пользовательские и некоторые встроенные сервисы могут быть настроены отдельно:

| Протокол/Конечная точка | Типичное использование |
| --- | --- |
| OpenAI Chat Completions | Большинство чат-моделей, совместимых с OpenAI |
| OpenAI Responses | Модели, использующие API Responses |
| Anthropic Messages | Нативные или совместимые с API Messages модели Claude |
| Google Generate Content | Нативные или совместимые интерфейсы Gemini |

Наличие нескольких протоколов в одном шлюзе не означает, что каждая модель поддерживает все конечные точки. Тип конечной точки модели должен соответствовать фактическому протоколу на стороне сервера.

### Пользовательские заголовки запроса

В **Настройках запроса** можно установить дополнительные заголовки запроса списком или в формате JSON.

Добавляйте только тогда, когда это явно требуется в документации шлюза, например, идентификатор арендатора или идентификатор проекта. Не дублируйте заголовки аутентификации, управляемые Cherry Studio, и не указывайте API Key в нескольких местах одновременно.

### Опции API поставщика услуг

Кнопка молнии рядом с названием поставщика может предоставить:

- Формат содержимого массива;
- Роль `developer`;
- Stream Options;
- Service Tier;
- Переключатель рассуждений (thinking switch) или детализация (verbosity);
- Настройки кэша промптов Anthropic.

Эти опции изменят только формат запроса и не предоставят серверу возможности, которые он изначально не поддерживал. При получении ошибок `400`, неизвестных параметров или ошибок формата ответа сначала восстановите значения по умолчанию.

## Список синхронизированных моделей

Нажмите **Загрузить** в списке моделей под поставщиком, и Cherry Studio получит доступные модели от поставщика, отобразив сначала предварительный просмотр синхронизации.

Предварительный просмотр обычно различает:

- Новые модели, добавленные на стороне сервера и доступные для локального подключения;
- Модели, которые уже существуют локально и всё ещё присутствуют на стороне сервера;
- Модели, существующие локально, но отсутствующие в списке на стороне сервера;
- Элементы, которые пользователь может выбрать для включения, отключения или сохранения.

Примените изменения только после подтверждения выбора; не предполагайте, что загрузка автоматически активирует все модели на стороне сервера.

Если поставщик не предоставляет интерфейс списка моделей или прокси не реализовал соответствующий интерфейс, вы можете вручную создать модель с помощью **Добавить**.

## Ручное добавление и редактирование моделей

Для ручного добавления требуется точный **ID модели**. ID модели — это значение, отправляемое на сервер в запросе, и оно должно полностью совпадать с документацией поставщика услуг.

Также можно установить:

- Отображаемое имя;
- Название группы;
- Тип конечной точки;
- Контекстное окно;
- Максимальное количество входных и выходных токенов;
- Возможности модели.

Часто используемые возможности включают:

- Зрение (Vision);
- Поиск в интернете по умолчанию (Native Web Search);
- Рассуждение (Reasoning);
- Вызов инструментов (Tool Calling);
- Встраивание (Embedding);
- Переранжирование (Re-ranking).

{% hint style="warning" %}
Пометка возможностей сообщает Cherry Studio только о том, как следует использовать модель, и не меняет возможности на стороне сервера. Неправильная пометка обычной модели как визуальной, с поиском в интернете или вызывающей инструменты может привести к сбою запроса или некорректной интеграции внешних инструментов.
{% endhint %}

Модели для встраивания и переранжирования предназначены для процессов поиска, таких как базы знаний, и не должны использоваться как обычные диалоговые модели.

## Видимость модели и проверка работоспособности

Переключатели поставщика услуг и переключатели моделей — это два независимых уровня управления:

1. Поставщик услуг должен быть включен;
2. Конкретная модель также должна быть включена.

Инструмент списка моделей позволяет:

- Искать модели;
- Фильтровать по возможностям;
- Пакетно включать или отключать видимые модели;
- Выполнять проверку работоспособности модели;
- Загружать модели с сервера;
- Добавлять модели вручную.

Проверка работоспособности подходит для быстрой проверки нескольких моделей; проверка подключения подходит для проверки указанного Key с указанной моделью. Оба действия могут инициировать реальные запросы к API и повлечь небольшие расходы.

## Добавление пользовательского провайдера

Нажмите **+** рядом с полем поиска провайдеров, чтобы создать пользовательского провайдера.

Основной процесс:

1. Введите название провайдера;
2. Выберите или загрузите иконку;
3. Укажите основной Base URL;
4. Опционально введите первый API Key;
5. При необходимости раскройте **Больше конечных точек** для заполнения адресов других протоколов;
6. После создания перейдите на страницу деталей, чтобы дополнить ключи и модели;
7. Активируйте провайдера и выполните проверку соединения.

По умолчанию при создании пользовательского провайдера основным конечным пунктом является OpenAI Chat Completions. Если целевой сервис поддерживает только Anthropic, Google или Responses API, необходимо явно выбрать правильный протокол в настройках конечных точек и моделей.

Вы также можете **скопировать провайдера** из предустановленных настроек для создания независимых экземпляров конфигурации. Например, если у одного шлюза есть тестовый и продакшн адреса, вы можете дать им разные имена, настроить ключи и статусы активации отдельно.

## Рекомендуемый порядок настройки

Чтобы сузить область поиска неисправностей, рекомендуется:

1. Включить провайдера;
2. Указать ключ, который вы уверены в его работоспособности;
3. Оставить или проверить адрес API по умолчанию;
4. Загрузить или вручную добавить модель чата;
5. Убедиться, что эта модель включена;
6. Выполнить проверку соединения с использованием этого ключа и модели;
7. Вернуться на страницу чата и отправить короткое сообщение;
8. После того как базовый вызов работает нормально, добавляйте несколько ключей, пользовательские заголовки и расширенные конечные точки.

Не изменяйте сразу ключи, адреса, конечные точки, заголовки запросов и расширенные параметры — иначе будет трудно определить причину сбоя.

## Часто задаваемые вопросы

### Модель отсутствует в селекторе моделей, хотя поставщик подключен

Проверьте:

- Включена ли переключатель в правом верхнем углу поставщика;
- Добавлена ли целевая модель в список моделей;
- Включена ли сама целевая модель;
- Скрывает ли текущая страница модели с помощью фильтра по возможностям;
- Успешно ли сохранен ID модели.

### При проверке соединения нет доступных для проверки моделей

Сначала загрузите или вручную добавьте как минимум одну неранжированную модель и включите ее. Модели ранжирования нельзя использовать для обычной проверки соединения.

### Возвращается 401 или 403

Обычно это связано с аутентификацией или правами доступа:

- Полный ли ключ и не отозван ли он;
- Принадлежит ли ключ правильному проекту, региону или организации;
- Авторизована ли выбранная модель;
- Перекрывает ли пользовательский заголовок правильный заголовок аутентификации;
- Требует ли облачный сервис региона, проекта или версии API.

### Возвращается 404

Обратите особое внимание на:

- Содержит ли базовый URL необходимый путь версии или не содержит его;
- Не ошибочно ли приняли полный `/chat/completions` за обычный базовый URL;
- Соответствует ли тип конечной точки модели протоколу сервера;
- Реализует ли пользовательский шлюз список моделей и пути диалога;
- Требуют ли такие сервисы, как Azure, имя развертывания или версию API.

### Возвращается 400 или «Неизвестный параметр»

Восстановите опции API поставщика и возможности модели в значения по умолчанию, удалите ненужные пользовательские заголовки запроса и затем протестируйте самый простой текстовый диалог.

### Сбой загрузки моделей

Некоторые поставщики не предоставляют интерфейс списка моделей или шлюз проксирует только чат-интерфейс. В этом случае вы можете добавить модели вручную по официальному ID модели.

Успешная загрузка не означает, что каждая модель доступна для текущей учетной записи; необходимо подтвердить это с помощью проверки работоспособности или фактического диалога.

### Проверка соединения прошла успешно, но диалог все равно завершается неудачей

Проверка обычно охватывает только один ключ, одну модель и один базовый запрос. Продолжайте проверять:

- Является ли выбранная в диалоге та же самая модель;
- Есть ли недействительные ключи при ротации нескольких ключей;
- Выходят ли контекст, изображения, подключение к сети или вызовы инструментов за рамки возможностей модели;
- Установил ли помощник несовместимые пользовательские параметры;
- Возникли ли ограничения по лимитам, параллелизму или политике контента со стороны поставщика.

### Ключ был ротирован до недействительных учетных данных

Откройте список ключей, деактивируйте или удалите сбойный ключ, а затем проверьте оставшиеся ключи по отдельности. Пока недействительный ключ остается в активном состоянии, он будет участвовать в ротации.

## Безопасность и резервное копирование

- Не используйте скриншоты, созданные с реальными ключами;
- Не вставляйте полные заголовки запросов в обратную связь по вопросам;
- Не смешивайте продакшн-ключи и тестовые ключи в неразборчистых списках;
- Перед удалением поставщика услуг или очисткой данных создайте резервную копию;
- После резервного копирования или синхронизации повторно проверьте локальные пути, прокси и права доступа к облачным аккаунтам на целевом устройстве;
- При необходимости поделиться конфигурацией отдавайте в приоритете название поставщика услуг, структуру адреса и ID модели без учетных данных.
