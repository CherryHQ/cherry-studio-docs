# Вклад в код

Cherry Studio принимает вклад в функции, исправления ошибок, тесты, производительность, доступность и инструменты разработки. Текущая разработка V2 ведётся в ветке `main`. Перед началом уточните проблему, область изменений и способ проверки.

Репозиторий проекта: [CherryHQ/cherry-studio](https://github.com/CherryHQ/cherry-studio)

## Перед началом

Сначала прочитайте:

* [Руководство для участников](https://github.com/CherryHQ/cherry-studio/blob/main/CONTRIBUTING.md)
* [Кодекс поведения](https://github.com/CherryHQ/cherry-studio/blob/main/CODE_OF_CONDUCT.md)
* [Руководство разработчика](https://github.com/CherryHQ/cherry-studio/blob/main/docs/guides/development.md)
* [Правила разработки проекта](https://github.com/CherryHQ/cherry-studio/blob/main/CLAUDE.md)
* [Лицензия с открытым исходным кодом](https://github.com/CherryHQ/cherry-studio/blob/main/LICENSE)

Если вы планируете большую функцию, изменение пользовательского процесса или рефакторинг публичного интерфейса, сначала выполните поиск по [Issues](https://github.com/CherryHQ/cherry-studio/issues) и существующим Pull Request. Если обсуждения нет, сначала создайте Issue с описанием проблемы, цели и решения — это уменьшит дублирование и расхождение в направлении.

Для первого вклада можно начать с задач с метками:

* [good first issue](https://github.com/CherryHQ/cherry-studio/labels/good%20first%20issue)
* [help wanted](https://github.com/CherryHQ/cherry-studio/labels/help%20wanted)
* [kind/bug](https://github.com/CherryHQ/cherry-studio/labels/kind%2Fbug)

## Выберите правильную ветку

| Изменение | Базовая ветка | Целевая ветка PR |
| :--- | :--- | :--- |
| Текущие функции, разработка V2, рефакторинг, оптимизация и исправления | `main` | `main` |
| Минимальное исправление сопровождения выпущенной V1 | `v1` | `v1` |

Исправление V1 не попадает в `main` автоматически. Если та же проблема существует в текущей ветке разработки, создайте отдельный forward-port PR для `main`.

Не отправляйте коммиты прямо в ветку вышестоящего репозитория. Сначала сделайте fork, затем создайте краткосрочную рабочую ветку от правильной базовой ветки.

## Подготовьте среду разработки

Текущая ветка `main` закрепляет Node.js `24.11.1` в `.node-version` и pnpm `10.27.0` в `package.json`. Версии меняются при обновлении репозитория; при каждом начале работы ориентируйтесь на файлы своей локальной ветки.

### Windows: сначала включите символические ссылки

Репозиторий использует символические ссылки для синхронизации некоторых файлов. Пользователям Windows перед клонированием следует:

1. включить **режим разработчика** в системных настройках или выдать право создавать символические ссылки;
2. выполнить:

```powershell
git config --global core.symlinks true
```

3. после этого клонировать репозиторий. Если он был клонирован до включения ссылок, рекомендуется включить настройку и клонировать заново.

### Fork и клонирование

Сначала сделайте fork `CherryHQ/cherry-studio` на GitHub, затем выполните:

```bash
git clone https://github.com/YOUR_GITHUB_NAME/cherry-studio.git
cd cherry-studio
git remote add upstream https://github.com/CherryHQ/cherry-studio.git
git fetch upstream
git switch -c fix/short-description upstream/main
```

Замените `YOUR_GITHUB_NAME` и имя ветки своими значениями. Для функции можно использовать `feat/`, для исправления `fix/`, для документации `docs/`.

### Установите Node.js и зависимости

Установите требуемую версию Node.js менеджером, который поддерживает `.node-version` или `.nvmrc`. Например:

```bash
nvm install
nvm use
corepack enable
corepack pnpm install
```

Используйте закреплённый pnpm через Corepack. Не перезаписывайте `pnpm-lock.yaml` другой глобальной версией pnpm. Если зависимости не менялись, PR не должен содержать постороннее изменение файла блокировки.

### Создайте локальный файл окружения

```bash
cp .env.example .env
```

`.env` игнорируется Git. Указывайте только значения, нужные для локальной разработки, и не добавляйте реальные API Key, Token, Cookie и другие учётные данные в код, тесты, журналы и снимки экрана.

### Запустите приложение

```bash
corepack pnpm dev
```

При первом запуске сначала создаются файлы OpenAPI, затем открывается экземпляр Electron для разработки. Для отладки главного процесса или процесса рендерера можно использовать:

```bash
corepack pnpm debug
```

Если установка зависимостей или запуск завершились ошибкой, сначала проверьте версии Node.js и pnpm, убедитесь, что другой менеджер пакетов не изменил файл блокировки, а затем изучите первую ошибку в терминале.

## Начните изменение

### Изучите локальные правила

Cherry Studio — monorepo с главным процессом Electron, слоем preload, рендерером React и несколькими общими пакетами. Перед редактированием директории:

1. прочитайте `README.md` в ней и родительских директориях;
2. посмотрите близкие реализации того же типа и тесты;
3. найдите метки `@deprecated`, чтобы не расширять устаревающий интерфейс;
4. изменяйте только файлы, необходимые для текущей проблемы.

Слой рендерера не должен напрямую обращаться к API Node.js. Для межпроцессных возможностей используйте существующие границы preload и IPC. Для журналов применяйте проектный `loggerService`, не добавляйте новые `console.log`.

### Сделайте изменение проверяемым

При исправлении ошибки рекомендуется сначала добавить тест, который её воспроизводит. Для нового поведения добавьте тесты успешного, ошибочного и граничного сценария. Проект использует Vitest и предоставляет команды по областям:

```bash
corepack pnpm test:main
corepack pnpm test:renderer
corepack pnpm test:aicore
corepack pnpm test:shared
```

Каждый раз запускать всё необязательно. Во время разработки сначала выполняйте тест, наиболее близкий к изменению, а перед коммитом — полную проверку.

### Текст для пользователя

При добавлении или изменении текста интерфейса используйте существующий механизм локализации и не записывайте в компоненте строку только на одном языке. Выполните как минимум:

```bash
corepack pnpm i18n:check
corepack pnpm i18n:hardcoded:strict
```

Если требуется синхронизировать новые ключи, сначала прочитайте [руководство по локализации](https://github.com/CherryHQ/cherry-studio/blob/main/docs/guides/i18n.md), затем используйте соответствующие сценарии.

### Структура базы данных

При изменении Drizzle Schema создайте и добавьте соответствующую миграцию:

```bash
corepack pnpm db:migrations:generate
corepack pnpm db:migrations:check
```

Если после rebase конфликтуют номера миграций, не переименовывайте только SQL-файл и не редактируйте snapshot вручную. Создайте миграцию заново по документации репозитория и убедитесь, что цепочка миграций соответствует Schema.

## Проверка перед коммитом

Сначала просмотрите реальные изменения:

```bash
git status --short
git diff --check
git diff
```

Убедитесь, что нет временных файлов, учётных данных, личных путей, постороннего форматирования и случайного изменения файла блокировки.

Выполните тесты, наиболее относящиеся к изменению, затем полную проверку репозитория:

```bash
corepack pnpm build:check
```

`build:check` выполняет проверку правил кода, типов, OpenAPI, ссылок документации, тестов и других элементов. Проверки базы данных, строгой локализации, навыков или отдельных пакетов могут дополнительно выполняться в CI. Если изменение затрагивает эти области, заранее выполните соответствующие команды.

{% hint style="info" %}
Сценарии проверки и версия Node.js меняются вместе с `main`. Если команда на этой странице расходится с репозиторием, ориентируйтесь на `package.json`, `.node-version`, `CONTRIBUTING.md` и конфигурацию CI в текущей ветке.
{% endhint %}

## Создайте коммит

Проект требует небольшие сфокусированные Conventional Commit и DCO sign-off:

```bash
git add path/to/changed-file
git commit --signoff -m "fix(module-name): describe the change"
```

Обычные типы: `feat`, `fix`, `refactor`, `docs`, `test` и `chore`. Scope должен указывать конкретный модуль коротким именем kebab-case; не используйте слишком общее значение вроде `main`.

`--signoff` добавляет в сообщение коммита:

```text
Signed-off-by: Your Name <your.email@example.com>
```

Это означает, что у вас есть право передать вклад по лицензии проекта. Это не криптографическая подпись GPG или SSH.

## Синхронизируйтесь с upstream

Перед созданием PR обновите ветку до последней `main`:

```bash
git fetch upstream
git rebase upstream/main
```

Разрешите конфликты и заново выполните соответствующие проверки, затем отправьте свою ветку:

```bash
git push -u origin fix/short-description
```

Если ветка уже отправлялась и после rebase нужно обновить удалённую, убедитесь, что используете её только вы, и примените безопасный `--force-with-lease`. Не выполняйте прямой force push в общую ветку.

## Создайте Pull Request

При создании PR:

1. выберите базовым репозиторием `CherryHQ/cherry-studio`;
2. для V2 и текущей разработки выберите base `main`;
3. заполните в шаблоне состояние до и после, причину реализации, компромиссы, связанный Issue, Breaking Change и Release Note;
4. для видимого пользователю изменения приложите снимок или запись экрана и укажите систему тестирования и шаги проверки;
5. запросите Review только после готовности всех обязательных материалов.

Если направление ещё не определено или разработка продолжается, создайте **Draft PR**. Проектный CI для Draft PR пропускается, а Review не назначается автоматически. После готовности отметьте Ready for review.

Не Draft PR нового участника может сначала получить метку `needs-ok-to-test`, и CI не запустится сразу. После того как сопровождающий добавит в PR `/ok-to-test`, будет создан тестовый конвейер. Это обычная мера безопасности; не нужно многократно закрывать и открывать PR.

## Обработайте Review

После получения замечаний:

1. по отдельности уточните проблему и ожидаемое поведение;
2. добавьте в исходную ветку небольшие понятные исправления;
3. заново запустите затронутые тесты;
4. ответьте, где внесено изменение и как оно проверено;
5. передайте решённое обсуждение Reviewer для подтверждения.

Не удаляйте полезный тест, не ослабляйте тип и не обходите проверку безопасности только ради «зелёного CI». Если сбой не связан с текущим PR, приложите к PR журнал и способ воспроизведения и попросите сопровождающего принять решение.

## Частые вопросы

### После установки зависимостей файл блокировки значительно изменился

Обычно не совпадают версии Node.js или pnpm. Отмените непреднамеренное изменение файла блокировки, заново подготовьте среду по `.node-version` и `packageManager`, затем выполните `corepack pnpm install`.

### В Windows неправильно работают навыки или синхронизируемые файлы

Убедитесь, что до клонирования были включены режим разработчика и `core.symlinks=true`. Если символические ссылки репозитория были извлечены как обычные файлы, включите настройку и клонируйте заново.

### CI не запускается

Сначала проверьте, не остаётся ли PR в состоянии Draft. Новому участнику также следует проверить метку `needs-ok-to-test` и дождаться, пока сопровождающий выполнит `/ok-to-test`.

### Неясно, требуется ли новый Issue

Небольшое и понятное исправление можно отправить напрямую как PR, указав в описании шаги воспроизведения. Большую функцию, изменение интерфейса или задачу с несколькими вариантами решения рекомендуется сначала согласовать в Issue.

Для вклада в документацию прочитайте [Вклад в документацию](docs.md). По другим вопросам обратитесь к сообществу через раздел [Отзывы и предложения](../question-contact/suggestions.md).
