# Участие в документации

Документация сообщества Cherry Studio хранится в репозитории Markdown и публикуется через GitBook. Вы можете внести изменения с помощью Pull Request на GitHub или, получив права редактора, через Change Request в GitBook.

* Репозиторий документации: [CherryHQ/cherry-studio-docs](https://github.com/CherryHQ/cherry-studio-docs)
* Код продукта: [CherryHQ/cherry-studio](https://github.com/CherryHQ/cherry-studio)
* Опубликованная документация: [docs.cherryai.com.cn](https://docs.cherryai.com.cn/)

Для пакетных обновлений, изменений на нескольких языках и страниц, где требуется сверка с кодом, используйте прежде всего GitHub. GitBook подходит для небольших правок текста или случаев, когда нужны визуальные комментарии.

## Сначала определите объем работы

Перед отправкой ответьте на четыре вопроса:

1. Вы изменяете существующую страницу или добавляете новую?
2. Какой версии Cherry Studio или какому поведению в `main` соответствует содержание?
3. Какие языки автор способен надежно проверить?
4. Нужны ли снимки экрана продукта и дополняют ли они сведения, которые нельзя ясно передать текстом?

Если материал касается текущих функций, названий настроек, возможностей моделей или путей хранения данных, сначала сверьтесь с кодом продукта в `main` и фактическим интерфейсом. Не копируйте без проверки старую документацию, сторонние статьи или результат, созданный моделью.

## Структура документации

Упрощенный китайский находится в корне репозитория, остальные опубликованные языки — в следующих каталогах:

| Язык | Каталог | Файл оглавления |
| :--- | :--- | :--- |
| 简体中文 | корень репозитория | `SUMMARY.md` |
| 中文（繁體） | `i18n/traditional-chinese/` | `i18n/traditional-chinese/SUMMARY.md` |
| English | `i18n/english/` | `i18n/english/SUMMARY.md` |
| 日本語 | `i18n/japanese/` | `i18n/japanese/SUMMARY.md` |
| Русский | `i18n/russian/` | `i18n/russian/SUMMARY.md` |

По умолчанию GitBook использует файл `README.md` в корне как главную страницу, а `SUMMARY.md` — как оглавление боковой панели. У каждого языка есть отдельный каталог и `SUMMARY.md`; иерархия и названия страниц должны оставаться согласованными в соответствующем языке.

## Способ 1: внести изменения через GitHub

### 1. Создайте fork и клонируйте его

Создайте fork репозитория документации на GitHub, затем выполните:

```bash
git clone https://github.com/YOUR_GITHUB_NAME/cherry-studio-docs.git
cd cherry-studio-docs
git remote add upstream https://github.com/CherryHQ/cherry-studio-docs.git
git fetch upstream
git switch -c docs/short-description upstream/main
```

### 2. Измените существующую страницу

Сохраните прежний путь файла и редактируйте соответствующий Markdown напрямую. Произвольное перемещение или переименование файла изменит URL страницы. Если путь действительно нужно изменить, укажите в PR старый и новый адреса, чтобы сопровождающий подтвердил перенаправление.

Если вы меняете несколько языков, редактируйте файлы отдельно в каталогах каждого языка. Не заменяйте содержимое других языков текстом на упрощенном китайском и не оставляйте в английской или японской странице снимки китайского интерфейса.

### 3. Добавьте новую страницу

Для новой страницы требуется как минимум:

1. Файл Markdown на упрощенном китайском.
2. Ссылка в подходящем разделе `SUMMARY.md`.
3. Страницы на других языках, которые можно надежно проверить, и ссылки на них в соответствующих `SUMMARY.md`.
4. Локальные изображения, используемые страницей.
5. Ссылки на новую страницу с подходящей родительской страницы или соседнего руководства.

Используйте для имени файла стабильное и понятное английское название либо следуйте стилю существующего каталога. Не включайте в путь дату, номер версии или рекламный заголовок, если страница не относится исключительно к этой версии.

Если вы пока не можете надежно перевести какой-либо язык, не отправляйте непроверенный машинный перевод. Укажите отсутствующие языки в описании PR, чтобы сопровождающие могли организовать дальнейшую работу.

## Требования к качественной документации продукта

Структура зависит от задачи, но обычно должна включать:

* **Назначение**: что читатель сможет сделать после изучения страницы.
* **Предварительные условия**: нужные версия, модель, учетная запись, файл или разрешение.
* **Шаги**: актуальные названия элементов интерфейса и реальный порядок действий.
* **Результат**: что отображается или создается при успехе и где это сохраняется.
* **Ограничения**: различия платформ, стоимость, конфиденциальность, передача данных и необратимые действия.
* **Устранение неполадок**: наиболее частые причины сбоев, которые можно проверить на практике.
* **Следующий шаг**: ссылка на функцию, которую логично использовать дальше.

Объяснение причин должно быть кратким и помогать принять решение. Не включайте процесс написания, внутренние обсуждения, непроверенный контекст или повторяющиеся рекламные заявления.

### Требования к тексту

* Заголовки и названия кнопок должны соответствовать текущему интерфейсу.
* В одном шаге описывайте одно действие, а его результат указывайте сразу после действия.
* Изменяемые цены, списки моделей и акции упоминайте только при необходимости и отмечайте, что актуальна текущая страница поставщика.
* Не приравнивайте совместимый API к полной поддержке всех возможностей.
* Не обещайте, что сторонний сервис навсегда останется бесплатным и доступным или всегда будет возвращать одинаковый результат.
* Для рискованных операций укажите резервное копирование, необходимые права и способ отката.
* Не помещайте API Key, Token, Cookie, личные пути и реальные диалоги в текст или примеры кода.

## Требования к снимкам экрана

Используйте снимки экрана только для поиска точки входа, объяснения сложного состояния или демонстрации результата. Если текст уже все ясно объясняет, не добавляйте изображения лишь ради ощущения «полноты».

### Размер и композиция

Снимки настольного приложения Cherry Studio должны соответствовать единым параметрам:

* Физический размер: `1920 × 1200`
* Соотношение сторон: `16:10`
* DPR: `2`
* На одной странице сохраняйте одинаковые размер окна, область кадрирования и визуальный масштаб

Не делайте один снимок из одной серии чрезмерно широким, а другой почти квадратным. По возможности сохраняйте полный контекст операции, но обеспечьте четкую видимость нужного элемента управления.

### Несколько языков

Страницы на упрощенном китайском, 繁體中文, English, 日本語 и Русский должны использовать интерфейс продукта на соответствующем языке. Текст диалога, имя ассистента, пример имени файла и результат также должны соответствовать языку страницы.

Если часть интерфейса действительно не переведена на нужный язык, опишите это состояние продукта в PR. Не подменяйте локализацию снимком на другом языке.

### Конфиденциальность и файлы

* Используйте вымышленные учетные записи, ассистентов, каталоги и диалоги.
* Скрывайте API Key, Token, адреса электронной почты, имена пользователей, личные каталоги и уведомления.
* Не используйте базы данных и базы знаний с реальными пользовательскими данными.
* Храните изображения в `.gitbook/assets/` и присваивайте им уникальные понятные имена.
* В Markdown используйте относительные пути и добавляйте alt-текст, объясняющий назначение изображения.
* Не ссылайтесь на временные URL загрузки с ограниченным сроком, закрытые ссылки Feishu или абсолютные пути на локальном компьютере.

Рекомендуются PNG или WebP. Сохраняйте четкость, но избегайте бессмысленных больших пустых областей и неоправданно крупных файлов.

## Markdown и GitBook

Репозиторий использует обычный Markdown, а также блоки подсказок и изображений GitBook. При изменении придерживайтесь оформления соседних страниц.

### Внутренние ссылки

Используйте относительные пути:

```markdown
[智能体](../advanced-basic/agent.md)
```

Главная страница каталога может ссылаться на каталог или `README.md`, но сначала убедитесь, что целевой файл существует. Не заменяйте внутреннюю ссылку полным URL опубликованного сайта: иначе Preview ветки и страницы других языков будут возвращать читателя в рабочую версию.

### Блоки подсказок

Используйте их только для сведений, которые действительно нужно выделить:

```markdown
{% hint style="warning" %}
执行前先备份数据。
{% endhint %}
```

Не перегружайте одну страницу множеством блоков подсказок. Обычные шаги и дополнительные пояснения оформляйте абзацами или списками.

### Файл оглавления

`SUMMARY.md` определяет иерархию боковой панели GitBook. При добавлении, перемещении или переименовании страницы проверьте `SUMMARY.md` соответствующего языка:

```markdown
* [Agent 案例](../advanced-basic/agent-an-li/README.md)
  * [黄金市场复盘 Agent](../advanced-basic/agent-an-li/gold-price-case.md)
```

Один файл Markdown не должен упоминаться несколько раз в одном `SUMMARY.md`.

## Локальная проверка

Перед отправкой выполните как минимум:

```bash
git status --short
git diff --check
git diff -- SUMMARY.md
```

Также вручную убедитесь в следующем:

* Все новые файлы Markdown и изображения отслеживаются Git.
* Пути в `SUMMARY.md` существуют, а отступы правильно отражают иерархию.
* Относительные ссылки и пути изображений на странице существуют.
* Текст и снимки пяти языков не перемешаны между собой.
* Все блоки кода, подсказок и frontmatter закрыты.
* Нет временных URL, реальных секретов, личных каталогов и дубликатов файлов, созданных редактором.

Разметку Markdown можно проверить на GitHub, но отображение GitHub и GitBook не полностью совпадает. Сложные блоки подсказок, размеры изображений, иерархию боковой панели и переходы между страницами дополнительно проверьте в GitBook Preview.

## Создайте Pull Request

Создайте коммит и отправьте ветку:

```bash
git add path/to/page.md SUMMARY.md .gitbook/assets/
git commit -m "docs(section): update page title"
git push -u origin docs/short-description
```

В описании PR укажите как минимум:

* Какие страницы изменены или добавлены.
* Соответствующую версию продукта, место в коде или официальный источник.
* Завершенные и еще не готовые языки.
* Добавленные или замененные снимки экрана.
* Выполненные проверки ссылок, структуры и отображения.
* Изменялись ли путь страницы или боковая панель.

Если PR еще не готов, его можно создать как Draft. Выполняйте слияние только после того, как сопровождающие проверят текст, факты, изображения и языки.

## Preview и публикация

После подключения репозитория документации к GitBook можно использовать двустороннюю синхронизацию GitHub и GitBook, но **репозиторий и ветку для синхронизации задает администратор GitBook**. Отправка PR не изменяет опубликованную документацию немедленно.

Если конфигурация GitBook отвечает требованиям, в PR появится проверка состояния с URL Preview. Учитывайте следующее:

* Для доступа к Preview обычно требуется вход в GitBook.
* По соображениям безопасности Preview может по умолчанию не создаваться для PR из fork. Администратор может изменить эту настройку.
* Preview может быть недоступен, если сайт не опубликован или использует особые ограничения доступа.

Поэтому не обещайте в описании PR, что GitBook Preview сможет открыть любой пользователь. Если автоматического Preview нет, сопровождающий предоставляет среду проверки или использует внутренний Preview до слияния.

Только после слияния PR с веткой, к которой сейчас подключен GitBook, коммит входит в процесс синхронизации и публикации GitBook. Права на слияние и официальную публикацию контролируют сопровождающие.

Официальные материалы GitBook:

* [Git Sync](https://gitbook.com/docs/integrations/git-sync)
* [GitHub Pull Request Preview](https://gitbook.com/docs/getting-started/git-sync/github-pull-request-preview)
* [Настройка README и SUMMARY](https://gitbook.com/docs/getting-started/git-sync/content-configuration)

## Способ 2: редактирование в GitBook

Чтобы получить права редактора GitBook, отправьте письмо на `support@cherry-ai.com` с темой «Запрос прав редактора Cherry Studio Docs» и укажите:

* Адрес электронной почты учетной записи GitBook.
* Разделы и языки, которые вы хотите поддерживать.
* Соответствующий опыт работы с документацией или продуктом.
* Планируемые изменения.

Получив права, создайте Change Request в GitBook вместо прямого изменения опубликованного содержимого. После самопроверки пригласите сопровождающего на Review. При слиянии Change Request GitBook синхронизирует изменения с соответствующей веткой Git в соответствии с настройками администратора.

Для пакетных изменений, перестройки нескольких языков и массовой замены изображений по-прежнему рекомендуется ветка GitHub: так удобнее проверять отдельные файлы и запускать автоматические проверки.

## Действия после Review

Сопровождающий может попросить исправить факты, сократить число снимков, добавить источники или унифицировать язык. При обновлении:

1. Изменяйте только область, которой касается отзыв.
2. Сохраняйте одинаковую структуру пяти языков.
3. После изменения снимков снова проверьте язык, размер и конфиденциальность.
4. В ответе укажите, что изменено и как это проверено.

Если проблема обнаружена после слияния документации, исправьте ее новым PR. Не скрывайте ошибку удалением истории или прямой перезаписью опубликованной ветки.

О внесении изменений в код читайте в разделе [Участие в разработке](code.md). Если вы не уверены, где описать проблему, сначала откройте страницу [Обратная связь и предложения](../question-contact/suggestions.md).
