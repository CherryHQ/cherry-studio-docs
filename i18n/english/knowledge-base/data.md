# Knowledge Base Data

This page explains where Cherry Studio stores knowledge base data, what content might be sent to model providers, and how to delete, back up, and migrate that data safely.

If you only want to create and use a knowledge base, start with the [Knowledge Base Tutorial](knowledge-base.md).

## What a Knowledge Base Stores

V2 knowledge base data is not a single file that can be copied on its own. It consists of several types of data that work together.

| Data | Main contents | Purpose |
| --- | --- | --- |
| Knowledge base metadata | Name, group, model, chunking, and retrieval configuration | Enables the app to identify and manage the knowledge base |
| Data source records | Original path or URL, type, status, and error information | Tracks imported content and processing progress |
| Vector index | Document passages, vectors, and retrieval fields | Supports retrieval tests and chat retrieval |
| File records and processing artifacts | Original file references, parsed text, and related data | Supports source previews, reindexing, and document processing |

Metadata and data source records are stored in Cherry Studio's main SQLite database. Each knowledge base also has its own local libSQL vector store file.

{% hint style="warning" %}
Do not back up only a knowledge base's vector file. The vector file must remain consistent with the knowledge base ID, data source records, and model configuration in the main database. Restoring it by itself usually does not produce a complete knowledge base.
{% endhint %}

## Are Local Files Copied?

When you add a local file to a knowledge base, Cherry Studio records the file's **original absolute path** and associates it through a file record. The original file remains in its existing location and is not moved when you add it to the knowledge base.

This has several direct consequences:

* Moving, renaming, or deleting the original file can cause previews and reindexing to fail
* An existing vector index does not update automatically when the original file changes
* After modifying the original file, you must manually reindex it from the knowledge base
* When backing up Cherry Studio data, you must back up external original files separately

Intermediate artifacts generated by a file processor might be stored in Cherry Studio's own data directory, but they are not a substitute for long-term backups of the original files.

## Data Storage Locations

Knowledge base data is located in Cherry Studio's user data directory. The default location is usually:

| System | Default user data directory |
| --- | --- |
| macOS | `~/Library/Application Support/CherryStudio` |
| Windows | `%APPDATA%\CherryStudio` |
| Linux | `~/.config/CherryStudio` |

The actual directory can differ based on installation method, app version, development environment, or a custom data directory. Use the current path shown under **Settings → Data → Data Directory** as the source of truth.

Typical V2 content directly related to knowledge bases includes:

* `cherrystudio.sqlite` at the root of the user data directory: knowledge base and data source metadata
* `Data/KnowledgeBase`: vector store files organized by knowledge base
* `Data/Files`: files and processing artifacts managed by Cherry Studio

{% hint style="info" %}
These internal paths are provided to clarify backup scope. Do not modify the files manually while the app is running. To change the entire data directory, see [Change Storage Location](../personalization-settings/storage.md).
{% endhint %}

## What Content Leaves Your Device?

“The knowledge base is stored locally” does not mean “the entire processing workflow runs locally.” Whether content is sent to external services depends on the processors and models you choose.

### Document Processing

If you use an online document parsing or OCR service, the original file or its content might be sent to the corresponding provider. With a local processor, this step can remain on your device.

### Indexing

When you use an online embedding model, the chunked text passages are sent to the embedding provider, and the returned vectors are stored locally. Reindexing calls the embedding service again.

### Retrieval and Reranking

When querying the knowledge base, the user's question is processed by the embedding model. If an online reranking model is enabled, the question and candidate passages are also sent to the reranking provider.

### Answer Generation

When a knowledge base is used in a chat, the user's question and retrieved passages are sent to the current chat model as context.

### Webpage Import

When you import a URL or Sitemap, Cherry Studio accesses the target website. Its server might record the IP address, access time, and request details.

{% hint style="warning" %}
Before processing sensitive material such as contracts, medical information, or internal code, review all four stages: document processing, embedding, reranking, and the chat model. Switching only the chat model to a local model does not guarantee that the other stages make no outbound requests.
{% endhint %}

## Reduce Data Sent Externally

If your sources cannot be sent to third parties:

1. Use local document parsing and OCR capabilities.
2. Run a local embedding model through Ollama, LM Studio, or a similar tool.
3. Do not enable an online reranking model, or replace it with a local service.
4. Select a local model for the chat stage.
5. Avoid importing internal webpages that require authentication.

For local model configuration, see [Embedding Models](emb-models-info.md) and the relevant model provider guides.

## What Happens When You Delete Data?

### Delete a Data Source

When you delete a data source, Cherry Studio removes its record and vector passages. For a folder or Sitemap, expanded child items are processed as well.

Deleting a file data source from a knowledge base **does not delete the original file from disk**.

### Delete a Chunk

Deleting an individual passage from the chunk details removes only that passage's retrieval data; it does not modify the original file. If you later reindex the data source, the deleted passage might be generated again according to the current chunking rules.

### Delete an Entire Knowledge Base

When you delete a knowledge base, Cherry Studio first stops its related background tasks, then deletes its vector store and records from the main database.

This operation does not delete the external original files referenced during import, but it does remove the knowledge base configuration and existing index. Before deleting, confirm that you have a complete backup that can be restored.

## Back Up a Knowledge Base

### Recommended Method

1. Use the built-in backup feature under **Settings → Data**.
2. If you need to restore the complete knowledge base, do not enable **Skip file data**.
3. Back up all external original files and folders separately.
4. Record the model provider, embedding model, and document processor you used.
5. Regularly verify in a secure environment that the backup can be restored.

The built-in backup option “Skip file data” excludes the `Data` content under the user data directory. This content includes knowledge base vector files and processing artifacts managed by Cherry Studio, so a backup made with this option is not a complete knowledge base backup.

### Copy the Entire Data Directory

To create a file-level snapshot, quit Cherry Studio completely before copying the **entire user data directory**, rather than copying only `Data/KnowledgeBase`.

While the app is running, the SQLite database and vector files might be receiving writes. Copying active files directly can produce an inconsistent snapshot.

### Checks After Restoring

After a restore, do not check only whether the knowledge base name appears. Also:

* Open the Data Sources list and confirm its statuses and counts
* Preview several sources
* Run a retrieval test with a fixed set of questions
* Verify cited sources in a chat
* Reindex external files that need to be updated

After moving between operating systems or major versions, or after changing the embedding model, validate the restore in a copy of the environment first. If external file paths change between devices, references to the original paths might stop working.

## Migration and Disk Space

Knowledge base disk usage mainly depends on:

* The size of original sources and processing artifacts
* The number of chunks
* The embedding vector dimensions
* The number of knowledge bases
* Data produced through repeated imports and reindexing

To move the data directory, use Cherry Studio's data directory setting and complete a backup before migration. After migrating, check at least one data source preview, retrieval test, and chat citation.

If you only need to free disk space, delete unused data sources or knowledge bases from within the app first. Do not delete internal database files directly.

## Frequently Asked Questions

### Do Original Files Remain After Deleting a Knowledge Base?

Yes. External local files referenced by a knowledge base are not deleted with the knowledge base. Deletion removes only the records and index managed by Cherry Studio.

### Can Retrieval Continue After Moving an Original File?

The existing index might temporarily continue returning old passages, but previews and reindexing will fail because the original path no longer works. Add the file again from its new path and verify the retrieval results.

### Can I Back Up Only `Data/KnowledgeBase`?

No. That directory contains only vector storage. It lacks metadata and data source relationships from the main database, and it does not include external original files.

### Does a Local Embedding Model Make Everything Fully Offline?

Not necessarily. You must also confirm that the document processor, reranking model, and chat model run locally, and check whether any external webpages were imported.

### Does Rebuilding an Index Incur Charges?

If you use usage-based online document processing, embedding, or reranking services, reindexing might incur model call charges again.
