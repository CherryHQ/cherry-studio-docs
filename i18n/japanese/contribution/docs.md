# ドキュメントへの貢献

Cherry Studio コミュニティ版のドキュメントは Markdown リポジトリで管理され、GitBook で公開されています。GitHub の Pull Request から貢献するか、編集権限を取得した後に GitBook の Change Request で変更できます。

* ドキュメントリポジトリ：[CherryHQ/cherry-studio-docs](https://github.com/CherryHQ/cherry-studio-docs)
* 製品コード：[CherryHQ/cherry-studio](https://github.com/CherryHQ/cherry-studio)
* 公開ドキュメント：[docs.cherryai.com.cn](https://docs.cherryai.com.cn/)

一括更新、複数言語の変更、コード上の事実確認が必要なページには GitHub を優先してください。少量の文言修正や、画面上でコメントしながら確認したい場合は GitBook を利用できます。

## 作業前に範囲を確認する

提出前に、次の 4 点を確認してください。

1. 既存ページの変更か、新しいページの追加か。
2. 内容が Cherry Studio のどのバージョン、または `main` のどの動作に対応するか。
3. 提出者が確実に検証できる言語はどれか。
4. 製品スクリーンショットが必要か、スクリーンショットが文章だけでは伝わらない情報を補えるか。

現在の機能、設定名、モデルの能力、データ保存先に関する内容は、最初に製品の `main` のコードと実際の画面で確認してください。古いドキュメント、第三者の記事、モデルが生成した内容をそのまま転記しないでください。

## ドキュメントの構成

簡体字中国語はリポジトリのルートにあり、その他の公開言語は次の場所にあります。

| 言語 | ディレクトリ | 目次ファイル |
| :--- | :--- | :--- |
| 简体中文 | リポジトリのルート | `SUMMARY.md` |
| 中文（繁體） | `i18n/traditional-chinese/` | `i18n/traditional-chinese/SUMMARY.md` |
| English | `i18n/english/` | `i18n/english/SUMMARY.md` |
| 日本語 | `i18n/japanese/` | `i18n/japanese/SUMMARY.md` |
| Русский | `i18n/russian/` | `i18n/russian/SUMMARY.md` |

GitBook はデフォルトでルートの `README.md` をホームページ、`SUMMARY.md` をサイドバーの目次として使用します。各言語には独立したディレクトリと `SUMMARY.md` があり、対応する言語内でページ階層と名称を揃える必要があります。

## 方法 1：GitHub から貢献する

### 1. Fork とクローン

GitHub でドキュメントリポジトリを fork し、次を実行します。

```bash
git clone https://github.com/YOUR_GITHUB_NAME/cherry-studio-docs.git
cd cherry-studio-docs
git remote add upstream https://github.com/CherryHQ/cherry-studio-docs.git
git fetch upstream
git switch -c docs/short-description upstream/main
```

### 2. 既存ページを変更する

既存のファイルパスを維持し、該当する Markdown を直接編集します。ファイルを不用意に移動または名前変更するとページ URL が変わります。パスの変更が本当に必要な場合は、PR に旧アドレスと新アドレスを記載し、メンテナーにリダイレクトを確認してもらってください。

複数の言語を変更する場合は、各言語のディレクトリにあるファイルを個別に編集します。簡体字中国語の本文で他言語を上書きしたり、英語や日本語ページで中国語 UI のスクリーンショットを使い続けたりしないでください。

### 3. ページを追加する

新しいページには、少なくとも次の項目が必要です。

1. 簡体字中国語の Markdown ファイル。
2. `SUMMARY.md` の適切なセクションに追加した入口。
3. 確実に検証できる他言語のページと、それぞれの `SUMMARY.md` の入口。
4. ページで使用するローカル画像。
5. 関連する上位ページまたは隣接するチュートリアルから新ページへのリンク。

ファイル名には、安定していて読みやすい英語名、または既存ディレクトリの命名規則を使用します。ページ自体がそのバージョンにだけ適用される場合を除き、日付、バージョン番号、宣伝文句をパスに含めないでください。

ある言語を確実に翻訳できない場合は、未確認の機械翻訳を提出しないでください。PR の説明に未対応の言語を記載し、メンテナーが後続作業を割り当てられるようにしてください。

## 良い製品ドキュメントの要件

構成はタスクによって異なりますが、通常は次の内容を含めます。

* **目的**：読み終えた後に何ができるようになるか。
* **前提条件**：必要なバージョン、モデル、アカウント、ファイル、権限。
* **手順**：現在の UI 名称を使い、実際の操作順に記載する。
* **結果**：成功時に何が表示・生成され、どこに保存されるか。
* **制約**：プラットフォーム差、料金、プライバシー、データ送信、取り消せない操作。
* **トラブルシューティング**：実際に判別できる、よくある失敗原因。
* **次のステップ**：続けて使う機能へのリンク。

「なぜこの操作をするのか」という説明は簡潔にし、読者の判断に役立つ内容だけにしてください。執筆過程、内部での議論、未検証の背景、重複する製品宣伝を含めないでください。

### 文言の要件

* 見出しやボタンの名前は現在の UI に合わせる。
* 1 つの手順では 1 つの操作だけを説明し、結果をその直後に記載する。
* 変動する価格、モデル一覧、キャンペーン情報は必要な場合だけ掲載し、サービスプロバイダーの最新ページが優先されることを明記する。
* 互換 API を完全な機能対応と同一視しない。
* 第三者サービスが永続的に無料・利用可能であることや、常に同じ結果を返すことを保証しない。
* 高リスク操作には、バックアップ、権限、ロールバック方法を記載する。
* API Key、Token、Cookie、個人のパス、実際の会話を本文やコード例に含めない。

## スクリーンショットの規則

スクリーンショットは、入口の位置を示す、複雑な状態を説明する、または結果を見せる場合にだけ使用します。文章だけで十分に理解できる場合は、「完成して見えるようにする」ためだけに追加する必要はありません。

### サイズと構図

Cherry Studio のデスクトップスクリーンショットは、次の仕様で統一します。

* 物理サイズ：`1920 × 1200`
* アスペクト比：`16:10`
* DPR：`2`
* 同じページ内では、ウィンドウサイズ、切り抜き範囲、表示比率を揃える

同じ組のスクリーンショットで、一方を極端に横長、もう一方を正方形に近い形にしないでください。操作の文脈をできるだけ残しながら、対象のコントロールが明確に見えるようにします。

### 多言語

簡体字中国語、繁體中文、English、日本語、Русскийのページでは、それぞれの言語に対応した製品 UI を使用します。会話内容、アシスタント名、サンプルファイル名、結果のテキストもページの言語に合わせてください。

対象言語に未翻訳の画面が実際に存在する場合は、その製品状況を PR に記載してください。別言語のスクリーンショットで、ローカライズ済みであるかのように見せないでください。

### プライバシーとファイル

* 架空のアカウント、アシスタント、ディレクトリ、会話内容を使用する。
* API Key、Token、メールアドレス、ユーザー名、個人ディレクトリ、通知を隠す。
* 実際のユーザーデータを含むデータベースやナレッジベースを使用しない。
* 画像は `.gitbook/assets/` に保存し、重複しない分かりやすいファイル名を付ける。
* Markdown では相対パスを使い、画像の用途を説明する alt テキストを付ける。
* 有効期限付きの一時ダウンロード URL、非公開の Feishu リンク、ローカルの絶対パスを参照しない。

PNG または WebP を推奨します。鮮明さは保ちつつ、意味のない大きな余白や不必要に巨大なファイルは避けてください。

## Markdown と GitBook

このリポジトリでは一般的な Markdown に加え、GitBook のヒントブロックと画像ブロックを使用しています。変更時は、近くのページの記法に合わせてください。

### 内部リンク

相対パスを使用します。

```markdown
[智能体](../advanced-basic/agent.md)
```

ディレクトリのトップページからディレクトリまたは `README.md` にリンクできますが、先に対象ファイルが存在することを確認してください。公開サイトの完全な URL をリポジトリ内ページの代わりに使うと、ブランチ Preview や多言語パスから本番サイトへ戻ってしまうため、避けてください。

### ヒントブロック

本当に強調する必要がある情報だけに使用します。

```markdown
{% hint style="warning" %}
执行前先备份数据。
{% endhint %}
```

同じページで多数のヒントブロックを連続して使用しないでください。通常の手順や補足説明は、段落またはリストにします。

### 目次ファイル

`SUMMARY.md` は GitBook のサイドバー階層を決定します。ページを追加、移動、名前変更するときは、対応する言語の `SUMMARY.md` も確認してください。

```markdown
* [Agent 案例](advanced-basic/agent-an-li/README.md)
  * [黄金市场复盘 Agent](advanced-basic/agent-an-li/gold-price-case.md)
```

同じ Markdown ファイルを、同じ `SUMMARY.md` から重複して参照しないでください。

## ローカルで確認する

提出前に、少なくとも次を実行します。

```bash
git status --short
git diff --check
git diff -- SUMMARY.md
```

さらに、次の点を目視で確認してください。

* 新しい Markdown と画像がすべて Git の追跡対象になっている。
* `SUMMARY.md` のパスが存在し、インデント階層が正しい。
* ページ内の相対リンクと画像パスが存在する。
* 5 言語の本文やスクリーンショットが相互に混在していない。
* コードブロック、ヒントブロック、frontmatter がすべて閉じている。
* 一時 URL、実際のシークレット、個人ディレクトリ、エディターが作った重複ファイルが含まれていない。

GitHub で Markdown のレイアウトを確認できますが、GitHub と GitBook のレンダリングは完全には同じではありません。複雑なヒントブロック、画像サイズ、サイドバー階層、ページ遷移は GitBook Preview でも確認してください。

## Pull Request を作成する

ブランチをコミットして push します。

```bash
git add path/to/page.md SUMMARY.md .gitbook/assets/
git commit -m "docs(section): update page title"
git push -u origin docs/short-description
```

PR の説明には、少なくとも次の内容を含めます。

* 変更または追加したページ。
* 対応する製品バージョン、コード位置、公式情報源。
* 完了済みと未対応の言語。
* 追加または差し替えたスクリーンショット。
* 実行したリンク、構造、表示の確認。
* ページパスまたはサイドバーの変更有無。

PR の準備が完了していない場合は Draft として作成できます。本文、事実、画像、言語をメンテナーが確認してからマージしてください。

## Preview と正式公開

ドキュメントリポジトリを GitBook に接続すると、GitHub と GitBook の双方向同期を利用できます。ただし、**同期するリポジトリとブランチは GitBook 管理者が設定します**。PR を提出しても、公開中のドキュメントは直ちに変更されません。

GitBook の設定条件を満たす場合、PR に Preview URL 付きのステータスチェックが表示されます。次の点に注意してください。

* Preview の閲覧には通常 GitBook へのログインが必要です。
* セキュリティ上の理由から、fork から作成した PR ではデフォルトで Preview が生成されない場合があります。管理者はこの設定を変更できます。
* サイトが未公開、または特定のアクセス制限を使用している場合も、Preview を利用できないことがあります。

したがって、誰でも GitBook Preview を開けると PR の説明で保証しないでください。自動 Preview がない場合は、メンテナーが確認環境を用意するか、マージ前に内部 Preview を使用します。

PR を GitBook が現在接続しているブランチへマージして初めて、コミットが GitBook の同期と公開フローに入ります。マージ権限と正式公開はメンテナーが管理します。

GitBook の公式リファレンス：

* [Git Sync](https://gitbook.com/docs/integrations/git-sync)
* [GitHub Pull Request Preview](https://gitbook.com/docs/getting-started/git-sync/github-pull-request-preview)
* [README と SUMMARY の設定](https://gitbook.com/docs/getting-started/git-sync/content-configuration)

## 方法 2：GitBook で編集する

GitBook の編集権限が必要な場合は、`support@cherry-ai.com` にメールを送り、件名を「Cherry Studio Docs 編集権限の申請」としてください。メールには次の内容を記載します。

* GitBook アカウントのメールアドレス。
* メンテナンスを希望するセクションと言語。
* 関連するドキュメントまたは製品の経験。
* 予定している変更。

権限を取得した後は、公開中の内容を直接変更せず、GitBook で Change Request を作成します。セルフチェックを完了してからメンテナーを Review に招待してください。Change Request をマージすると、GitBook は管理者の設定に従って変更を対応する Git ブランチへ同期します。

一括変更、複数言語にまたがる再構成、大量の画像差し替えには、ファイル単位でのレビューと自動チェックがしやすい GitHub ブランチを引き続き推奨します。

## Review 後の対応

メンテナーから、事実の修正、スクリーンショットの削減、情報源の追加、言語の統一を求められることがあります。更新時は次の手順に従います。

1. フィードバックに関係する範囲だけを変更する。
2. 5 言語の構造を揃える。
3. スクリーンショットを変更した場合は、言語、サイズ、プライバシーを再確認する。
4. 変更内容と検証結果を返信する。

ドキュメントのマージ後に問題が見つかった場合は、新しい PR で修正してください。履歴の削除や公開ブランチの直接上書きによって問題を隠さないでください。

コードへの貢献については、[コードへの貢献](code.md)を参照してください。問題をどこに書けばよいか分からない場合は、先に[フィードバックと提案](../question-contact/suggestions.md)を確認してください。
