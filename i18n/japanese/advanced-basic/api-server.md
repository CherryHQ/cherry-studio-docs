# API サーバー

API サーバーは、Cherry Studio に設定済みのモデル、MCP、ナレッジベース機能をローカル HTTP API として公開します。他のアプリケーションは、OpenAI または Anthropic 互換のリクエスト形式でこれらの機能を呼び出せるため、ツールごとにプロバイダーの API キーを設定し直す必要がありません。

主な用途：

* スクリプトやサードパーティ製ツールから、Cherry Studio に設定済みのモデルプロバイダーを再利用する。
* OpenAI Chat Completions または Anthropic Messages 形式で会話を実行する。
* 外部プログラムから MCP Server を照会したり、Cherry Studio のナレッジベースを検索したりする。
* Cherry Studio の Agent ページと一部の内部処理を支える。

{% hint style="info" %}
現在、Agent ページの利用には API サーバーが必要です。既存の Agent が検出されると、Cherry Studio はサーバーの自動起動を試みます。サーバーが停止している場合は、Agent ページに再度有効化するよう案内が表示されます。チャンネルとスケジュールタスクは独立したローカルのメインプロセスサービスを使用するため、API サーバーを別途有効にする必要はありません。
{% endhint %}

## サーバーを起動する

1. `設定 → API サーバー` を開きます。
2. ポートが使用可能であることを確認します。デフォルトは `23333` で、`1000`～`65535` の範囲に設定できます。
3. **起動** をクリックします。

起動すると、ページに **実行中**、サーバーアドレス、**API ドキュメント** ボタンが表示されます。標準設定のアドレスは次のとおりです。

```
http://127.0.0.1:23333
```

サーバーの実行中はポートを編集できません。変更する場合は、先に **停止** をクリックし、ポートを変更してから再起動してください。

Cherry Studio を次回起動したとき、次のいずれかの条件を満たすとサーバーの自動起動が試みられます。

* 前回、API サーバーが有効なままだった。
* Cherry Studio に Agent がすでに存在する。

{% hint style="warning" %}
API サーバーは Cherry Studio とともに動作します。アプリを終了するとローカル API も停止します。
{% endhint %}

## API キー

初回起動時に、Cherry Studio は `cs-sk-` で始まる API キーを生成してローカルに保存します。サーバーやアプリを再起動しても、キーが自動的に変更されることはありません。

保護された API は、次の 2 種類の認証ヘッダーに対応しています。

```
Authorization: Bearer YOUR_API_KEY
```

または：

```
x-api-key: YOUR_API_KEY
```

設定ページにはデフォルトで Bearer 形式が表示され、コピーボタンも用意されています。キーを変更する場合は、先にサーバーを停止してから **再生成** をクリックしてください。新しいキーが生成されると、古いキーは直ちに認証に使用できなくなります。

{% hint style="danger" %}
API キーを使うと、Cherry Studio で有効になっているモデルやデータ機能を呼び出せます。実際のキーをコードリポジトリ、スクリーンショット、ドキュメント、公開チャットに含めないでください。呼び出し元のプログラムには、環境変数で渡すことを推奨します。
{% endhint %}

## 利用可能な API

サーバーを起動したら、ページ右上の **API ドキュメント** を開くか、次の URL に直接アクセスします。

* `/api-docs`：Swagger 形式のインタラクティブドキュメント
* `/api-docs.json`：OpenAPI JSON

主な公開 API：

| 機能 | API |
|---|---|
| サーバーの状態 | `GET /health` |
| OpenAI 互換会話 | `POST /v1/chat/completions` |
| Anthropic 互換会話 | `POST /v1/messages` |
| プロバイダーを指定した Anthropic 互換会話 | `POST /{provider_id}/v1/messages` |
| MCP Server の一覧と詳細 | `GET /v1/mcps`、`GET /v1/mcps/:server_id` |
| ナレッジベースの一覧と詳細 | `GET /v1/knowledge-bases`、`GET /v1/knowledge-bases/:id` |
| ナレッジベース検索 | `POST /v1/knowledge-bases/search` |

`GET /`、`GET /health`、`/api-docs`、`/api-docs.json` には認証が不要です。モデル、MCP、ナレッジベース、およびその他の `/v1` API には API キーが必要です。

{% hint style="info" %}
現在の API には `GET /v1/models` がありません。サードパーティ製クライアントがモデル一覧を自動取得する必要がある場合は、モデル ID を手動で入力するか、モデル検出を省略できるクライアントであることを確認してください。
{% endhint %}

## 最初のリクエストを送信する

次の例では OpenAI 互換 API を呼び出します。`YOUR_API_KEY`、`provider-id`、`model-id` を実際の値に置き換えてください。

```bash
curl http://127.0.0.1:23333/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "provider-id:model-id",
    "messages": [
      {
        "role": "user",
        "content": "Cherry Studioを一文で紹介してください"
      }
    ]
  }'
```

ストリーミング出力が必要な場合は、リクエスト本文に次を追加します。

```json
{
  "stream": true
}
```

ストリーミングレスポンスには Server-Sent Events が使用され、`data: [DONE]` で終了します。

## モデル ID の入力方法

API は次の形式でモデルを特定します。

```
プロバイダーID:モデルID
```

たとえば、プロバイダー ID が `my-openai`、モデル ID が `gpt-4o-mini` の場合は、次のように入力します。

```
my-openai:gpt-4o-mini
```

ここで必要なのは Cherry Studio 内部のプロバイダー ID であり、設定ページに表示される名前と同じとは限りません。モデルは対象プロバイダーに追加済みで、利用可能である必要があります。コロンがない、プロバイダーが無効、またはモデルが存在しない場合はリクエストエラーになります。

API サーバーは、有効になっている OpenAI、Anthropic、Ollama、New API タイプのプロバイダーから利用可能なモデルを解決します。実際に利用できるモデル機能は、上流プロバイダーによって決まります。

互換 API ごとに制限が異なります。

* `/v1/chat/completions` は現在、OpenAI タイプのプロバイダーのみ受け付けます。
* `/v1/messages` と `/{provider_id}/v1/messages` は Anthropic Messages 互換リクエストに使用します。
* Cherry Studio の設定にプロバイダーが表示されていても、すべての API から呼び出せるとは限りません。

「プロバイダーがサポートされていない」というエラーが返された場合は、モデル名だけでなく、プロバイダーのタイプと使用中の API が一致しているかを先に確認してください。

## サードパーティ製クライアントで使用する

OpenAI Base URL をカスタマイズできるクライアントでは、通常、次のように設定します。

| 設定項目 | 値 |
|---|---|
| Base URL | `http://127.0.0.1:23333/v1` |
| API Key | 設定ページに表示される Cherry Studio API キー |
| Model | `プロバイダーID:モデルID` |

クライアントによっては `/v1` が自動的に追加されます。入力する前に、そのクライアントの Base URL に関する説明を確認してください。最終的なリクエストが `/v1/v1/chat/completions` になる場合は、どちらか一方の `/v1` を削除します。

一部のクライアントは、公開 HTTPS アドレスのみを受け付ける、`/v1/models` を必ず呼び出す、またはモデル ID にコロンを使用できない場合があります。このようなクライアントは、現在のローカル API を直接利用できません。

## セキュリティ境界

標準設定では `127.0.0.1` をリッスンするため、同じコンピューター上のプログラムだけが直接アクセスできます。設定ページで変更できるのはポートだけで、LAN 公開用のスイッチはありません。

以前のバージョンからアップグレードした場合は、過去のリッスンアドレスが保持されている可能性があります。設定ページの実行状態に表示される実際の URL を確認してください。`0.0.0.0` または LAN 内のアドレスが表示される場合は、それが意図した設定かどうかを直ちに確認してください。

リバースプロキシ、ポート転送、SSH トンネルなどを使って API を別のデバイスへ転送する場合は、追加のアクセス制御を自身で行う必要があります。

* HTTPS を必須にする。
* プロキシ層に接続元制限とレート制限を追加する。
* URL のクエリパラメーターで API キーを渡さない。
* キーを定期的に変更し、不要なときは転送を停止する。
* `/health` と API ドキュメント自体には認証が不要であることに注意する。

リッスンアドレスをインターネットへ直接公開しないでください。API はクロスオリジンリクエストを許可しているため、ブラウザーの同一オリジンポリシーだけではセキュリティ対策になりません。

## トラブルシューティング

### 起動できない、またはポートが使用中

エラーに `EADDRINUSE` が含まれている場合：

1. 同じポートを使用している可能性がある他の Cherry Studio インスタンスまたはローカルサービスを停止します。
2. 設定ページで、使用されていない別のポートに変更します。
3. macOS または Linux では `lsof -i :23333`、Windows では `netstat -ano | findstr :23333` を実行すると、ポートを使用しているプロセスを確認できます。

### 401 または 403 が返される

* `401` は通常、認証ヘッダーがない、Bearer の形式が正しくない、またはキーが空であることを示します。
* `403` は通常、キーが設定ページの現在の値と一致していないことを示します。
* キーを再生成した直後は、呼び出し元プログラムの環境変数または設定を更新してから再試行してください。

まず、次の認証不要のリクエストでサーバーがオンラインかを確認します。

```bash
curl http://127.0.0.1:23333/health
```

### モデル形式またはプロバイダーのエラーが返される

モデルが `プロバイダーID:モデルID` 形式であることを確認し、次の項目をチェックします。

* プロバイダーが有効になっている。
* プロバイダーのタイプが API サーバーでサポートされている。
* 対象モデルがそのプロバイダーのモデル一覧に存在する。
* 表示専用の名前ではなく、内部プロバイダー ID をリクエストに使用している。

API とプロバイダーのタイプが一致していることも確認してください。OpenAI Chat Completions は現在 OpenAI タイプのプロバイダーを必要とし、Anthropic Messages では Messages API を使用します。

### ナレッジベース API が 503 を返す

ナレッジベース API は、Cherry Studio のメインウィンドウから現在のナレッジベース状態を読み取る必要があります。メインウィンドウの準備ができていない、終了中、または内部状態を利用できない場合、API は `503` を返します。メインウィンドウを開いたままにし、アプリの読み込みが完了してから再試行してください。

### サードパーティ製クライアントから接続できない

* Cherry Studio と API サーバーの両方が引き続き実行中であることを確認します。
* クライアントが別のデバイス、コンテナー、または仮想マシン上で動作していないか確認します。その環境の `127.0.0.1` は、Cherry Studio が動作しているホストを指すとは限りません。
* Base URL で `/v1` が重複または欠落していないか確認します。
* `curl` で `/health` と対象 API を個別にテストし、ネットワーク、認証、リクエスト本文のどこに問題があるかを切り分けます。

さらに調査する場合は、`設定 → データ設定` からログディレクトリを開けます。ログを共有する前に、API キー、Token、個人のパス、業務データを検索してマスキングしてください。
